# Brehon Consensus app-plane feasibility brief

## Executive summary

Brehon Consensus can realistically integrate beyond Lemmy, Matrix, and PeerTube, but the integration class differs sharply by platform: the strongest candidates are platforms with (1) public or member-readable content APIs, (2) a local extension or bot surface that can enforce local sanctions without giving Brehon administrator credentials, and (3) stable addressable identities. The best additional app-plane candidates are Discourse, NodeBB, and Bluesky/AT Protocol labelers; the strongest confirmatory targets remain Lemmy, Matrix in non-E2EE rooms, and PeerTube. This conclusion follows from the documented Mastodon/PeerTube/Matrix/Discourse/NodeBB/AT Protocol APIs and extension surfaces, and from the fact that ActivityPub and AT Protocol already provide moderation-signalling rails that Brehon should reuse where possible rather than inventing a bespoke transport ([Mastodon status API](https://docs.joinmastodon.org/methods/statuses/), [PeerTube REST API reference](https://docs.joinpeertube.org/api-rest-reference.html), [Matrix Application Service API](https://spec.matrix.org/latest/application-service-api/), [Discourse API docs](https://docs.discourse.org/), [NodeBB plugin docs](https://docs.nodebb.org/development/plugins/), [Bluesky labels and moderation docs](https://docs.bsky.app/docs/advanced-guides/moderation)).

The core feasibility constraint is not whether Brehon can read public evidence; most candidates can expose public posts, videos, events, or messages. The decisive constraint is whether B-publish can be implemented as a small, locally run subscriber using a documented bot, application-service, plugin, or labeler surface, because Mastodon-style “silence/suspend” actions require local moderator or administrator authority even when the underlying ActivityPub object is public ([Mastodon admin account action API](https://docs.joinmastodon.org/methods/admin/accounts/), [Pleroma Admin API](https://docs.pleroma.social/backend/development/API/admin_api/), [Akkoma Admin API](https://docs.akkoma.dev/stable/development/API/admin_api/)).

Keet/Holepunch/Pear-style serverless P2P apps are blocked under Brehon’s present contract because the contract assumes an app-side public API for B-fetch and an app-side subscriber surface for B-publish, while Keet advertises direct end-to-end encrypted peer-to-peer exchange with no servers or third parties and Pear describes a zero-infrastructure P2P runtime rather than a community server with moderation APIs ([Keet privacy page](https://keet.io/), [Pear documentation](https://docs.pears.com/)).

## Rating method

A platform is rated **Strong** when all five requirements can be met by documented upstream mechanisms with only a local subscriber/bridge/plugin and no Brehon-held administrator credential. A platform is rated **Partial** when the core model can work for a constrained subset, such as public-only evidence, non-E2EE rooms, label-only sanctions, community-local moderation, or a local plugin that still needs elevated app-side authority. A platform is rated **Blocked** when the architecture lacks a readable server/API plane or enforceable subscriber plane under the stated B-fetch/B-publish/B-actor contract.

Requirement meanings are: **A** public/readable content API for B-fetch; **B** extension/bot/subscriber surface for B-publish; **C** stable per-user identity for B-actor mapping; **D** self-hostable open-source upstream; and **E** sanction primitives such as mute, timeout, content removal, posting restriction, ban, demonetisation, labels, or visibility controls.

## Strong candidates and concrete integration designs

### Lemmy: native app plane and cross-instance reference target

For a Lemmy-family integration, B-fetch should read posts, comments, communities, and users through Lemmy’s HTTP client/API surface, with the Brehon fork keeping the native path in-process where possible and separate Lemmy instances using the same API contract externally ([Lemmy JS client](https://join-lemmy.org/api/classes/LemmyHttp.html)). B-actor should map each local Lemmy person ID and ActivityPub actor URI to the Brehon actor ID at opt-in, because Lemmy communities and users already participate in ActivityPub federation and expose durable federation identifiers through the application data model ([Lemmy JS client](https://join-lemmy.org/api/classes/LemmyHttp.html)). B-publish should translate sanctions into local moderator operations such as post/comment removal, community ban, instance-level ban, lock, or report handling, because Lemmy’s user documentation describes moderator workflows for reports and content actions ([Lemmy moderation docs](https://join-lemmy.org/docs/users/04-moderation.html)).

The cross-instance design should not assume that one Brehon jury can directly mutate remote Lemmy instances; instead, each participating instance should run its own subscriber that maps Brehon sanction events into local moderator actions. This preserves Brehon’s “no app admin credentials” rule while allowing each instance to decide whether a sanction is binding, advisory, or filtered by local policy.

### Matrix: first reference integration, but only where evidence is visible

For Matrix, B-fetch can read room events via the Client-Server API when the subscriber/appservice is a room member or otherwise authorized, and it can read public-room metadata through Matrix’s room-directory and state APIs where public visibility allows it ([Matrix Client-Server API](https://spec.matrix.org/latest/client-server-api/)). B-publish should use an application service or bot user registered with a homeserver, because the Matrix Application Service API defines a privileged bridge model with namespaces and transaction delivery while mautrix documents the practical registration flow used by bridges ([Matrix Application Service API](https://spec.matrix.org/latest/application-service-api/), [mautrix appservice registration guide](https://docs.mau.fi/bridges/general/registering-appservices.html)).

The sanction mapping is strong when a Brehon appservice has room power levels: content removal maps to redaction, room exclusion maps to kick/ban, posting restriction maps to power-level changes, and timeouts can be implemented as scheduled power-level restoration. The limitation is structural: end-to-end encrypted rooms expose ciphertext to servers and bridges unless the bridge is deliberately designed as an encrypted participant with keys, so Brehon should require either non-E2EE governed rooms, explicit evidence upload by reporters, or an in-room bot/bridge that receives decryptable events.

B-actor should map Matrix MXIDs such as `@alice:example.org` to Brehon portable actor IDs, because Matrix user identifiers are globally scoped by homeserver domain and are stable enough for opt-in account linking under the B-actor model ([Matrix Client-Server API](https://spec.matrix.org/latest/client-server-api/)).

### PeerTube: planned next target, confirmed

PeerTube is a strong app plane because B-fetch can obtain videos, channels, accounts, comments, and metadata from PeerTube’s REST API, and public video/comment evidence aligns well with Brehon’s hashed-snapshot model ([PeerTube REST API reference](https://docs.joinpeertube.org/api-rest-reference.html)). B-publish should be implemented as a PeerTube plugin or local service that subscribes to Brehon events and invokes local moderation actions for videos, comments, accounts, and channels, because PeerTube has documented plugin and plugin-API surfaces for server-side extensions ([PeerTube plugins documentation](https://docs.joinpeertube.org/contribute/plugins), [PeerTube plugin API](https://docs.joinpeertube.org/api/plugins)).

B-actor should map PeerTube accounts/channels and their ActivityPub actor URLs to Brehon actor IDs, because PeerTube is a federated ActivityPub application and its objects are naturally addressable across instances ([PeerTube REST API reference](https://docs.joinpeertube.org/api-rest-reference.html)). Sanction translation can support removal or hiding of comments and videos, account/channel restrictions, comment-policy changes, and possibly demonetisation or distribution throttling where an instance has local monetisation or recommendation controls.

### Bluesky / AT Protocol: strongest “ride the rails” candidate for label sanctions

AT Protocol is the best non-ActivityPub candidate because its moderation model already separates identity, data, and moderation labels. AT Protocol roots identity in persistent DIDs, stores public content in content-addressed repositories, and distributes labels as signed metadata outside repositories ([AT Protocol specification](https://atproto.com/specs/atp), [AT Protocol overview](https://atproto.com/guides/overview)).

B-fetch can read public repository records and AT-URI-addressed content through XRPC/AppView/relay paths, and B-actor can map DIDs and handles to Brehon actor IDs. B-publish should be implemented as a Brehon labeler service rather than as an admin bot, because Bluesky’s moderation docs state that labelers publish labels through a labeling service, can receive reports, and can place labels on accounts or records that clients interpret as hide, warn, or ignore behavior ([Bluesky labels and moderation docs](https://docs.bsky.app/docs/advanced-guides/moderation)).

The sanction vocabulary should start as labels such as `brehon-timeout`, `brehon-hide`, `brehon-warning`, `brehon-member-suspended`, or community-specific labels, with client/appview policy deciding whether those labels hide, warn, downrank, or deny posting. Ozone is relevant because Bluesky open-sourced it as a labeling/moderation web interface, and the Bluesky moderation architecture notes that a labeler must implement `com.atproto.label.subscribeLabels` and `com.atproto.label.queryLabels`, while report intake can use `com.atproto.report.createReport` ([Bluesky moderation architecture blog](https://docs.bsky.app/blog/blueskys-moderation-architecture), [Ozone repository](https://github.com/bluesky-social/ozone)).

The main limitation is that labels are not the same as deletion: Brehon can publish authoritative community labels, but hard takedown or account suspension remains the job of a PDS, AppView, hosting provider, or network-level operator. This limitation is compatible with Brehon’s “no admin control” principle and is a feature if the target community wants portable, opt-in moderation rather than centralized removal.

### Discourse: high-value forum integration

Discourse is a strong additional app plane because B-fetch can read public topics/posts through the Discourse API and web JSON endpoints, and private categories can be handled only when the local subscriber or bot is a permitted participant ([Discourse API docs](https://docs.discourse.org/)). B-publish should be a locally installed Discourse plugin or a scoped local API-key service that receives Brehon sanction events and invokes Discourse’s internal moderation operations, because Discourse has a mature API-key model and a large plugin ecosystem ([Discourse API docs](https://docs.discourse.org/), [Discourse admin API-key discussion](https://meta.discourse.org/t/admin-api-keys/227244)).

B-actor should map Discourse numeric user IDs and usernames to Brehon actor IDs during opt-in. The sanction mapping is direct: remove or hide posts, silence or suspend users, close topics, rate-limit trust-level effects, restrict posting in categories, and annotate moderator notes. Brehon should avoid asking Discourse administrators to hand credentials to Brehon; the subscriber should run inside the Discourse deployment or under a scoped key controlled by the local community.

### NodeBB: high-value forum integration, especially for ActivityPub-aware communities

NodeBB is strong because it has a documented Read API, Write API, and plugin architecture, so B-fetch can read public topics/posts and B-publish can be implemented as a plugin or privileged local service ([NodeBB Read API](https://docs.nodebb.org/api/), [NodeBB Write API](https://docs.nodebb.org/api/write/), [NodeBB plugin docs](https://docs.nodebb.org/development/plugins/)). B-actor should map NodeBB user IDs and usernames to Brehon IDs, and in ActivityPub-enabled deployments it can also map federated actor identifiers where exposed.

The sanction mapping should cover post deletion/hiding, topic locking, user muting, category restrictions, temporary bans, and moderator flags. The plugin path is preferable to a generic external write API token because it can keep all privileged operations local to the NodeBB instance while exposing Brehon only to sanction events and public evidence hashes.

## Partial candidates and recommended constrained designs

### Mastodon, GoToSocial, Pleroma, and Akkoma

ActivityPub microblogging is a partial app-plane family. B-fetch is strong for public posts because Mastodon documents `GET /api/v1/statuses/:id` as public for public statuses and token-gated only for private statuses ([Mastodon status API](https://docs.joinmastodon.org/methods/statuses/)). B-actor is strong because ActivityPub actors are addressable by URLs and Mastodon account/status objects carry stable local IDs plus ActivityPub URIs ([Mastodon Account entity](https://docs.joinmastodon.org/entities/Account/), [Mastodon Status entity](https://docs.joinmastodon.org/entities/Status/)).

B-publish is partial because Mastodon’s account moderation endpoint `POST /api/v1/admin/accounts/:id/action` requires an admin-scoped user token and permissions such as Manage Users and Manage Reports, while Pleroma and Akkoma admin APIs similarly document administrator requirements for user and report actions ([Mastodon admin account action API](https://docs.joinmastodon.org/methods/admin/accounts/), [Pleroma Admin API](https://docs.pleroma.social/backend/development/API/admin_api/), [Akkoma Admin API](https://docs.akkoma.dev/stable/development/API/admin_api/)). A Brehon-compliant implementation therefore needs either a local instance plugin/sidecar that the instance admin controls, or a narrow local moderator account whose credentials never leave the instance.

Brehon should also reuse ActivityPub `Flag` and `Block` rails for reports and advisory sanctions where possible. Mastodon’s ActivityPub documentation says incoming `Flag` is transformed into a report for the moderation team and that Mastodon sends a `Flag` activity from the instance actor when reporting remote profiles or posts, but it also cautions that remote `Block` behavior is not guaranteed ([Mastodon ActivityPub documentation](https://docs.joinmastodon.org/spec/activitypub/)). This means Brehon can federate reports and advisories, but actual silencing/suspension remains local policy.

### Mbin and PieFed

Mbin is a plausible partial app plane because it has substantial API documentation and app-developer documentation, and its link-aggregator model is close to Lemmy’s evidence and sanction shape ([Mbin API docs](https://docs.joinmbin.org/api/), [Mbin app-developer docs](https://docs.joinmbin.org/app_developers/)). Brehon should integrate Mbin after confirming per-release endpoints for moderator actions, scoped credentials, and actor ID exposure.

PieFed is promising but less stable because public search results and developer discussions point to alpha Swagger docs and changing Lemmy-compatible API coverage rather than a mature, canonical upstream API contract ([PieFed API support discussion](https://github.com/mlemgroup/mlem/issues/1824), [PieFed API community](https://lemmy.world/c/piefed_api@piefed.social)). Brehon should treat PieFed as a later link-aggregator target and design an adapter that tolerates alpha endpoint changes.

### Mattermost, Rocket.Chat, and Zulip

Self-hosted team chat platforms are partial because their APIs and extension systems are strong, but their content is often private-by-default and their moderation authority is workspace-local. Mattermost has a REST API and server plugin SDK, but the local plugin must hold the authority to read channels and apply sanctions inside the workspace ([Mattermost API](https://api.mattermost.com/), [Mattermost server plugin SDK](https://developers.mattermost.com/integrate/reference/server/server-reference/)).

Rocket.Chat has REST APIs and Apps-Engine, so a locally installed app can subscribe to Brehon and apply workspace actions, but the integration should not assume public evidence or cross-workspace federated identity ([Rocket.Chat API docs](https://developer.rocket.chat/apidocs), [Rocket.Chat Apps-Engine overview](https://developer.rocket.chat/docs/rocketchat-apps-engine)). Zulip has message-fetching and event-queue APIs, but bot visibility and administrative actions are permission-bounded, so B-fetch should be limited to streams/topics where the bot is authorized and B-publish should use a local privileged service account or extension ([Zulip get messages API](https://zulip.com/api/get-messages), [Zulip event queue API](https://zulip.com/api/register-queue), [Zulip delete message API](https://zulip.com/api/delete-message)).

B-actor should map local user IDs and emails/usernames only after opt-in; these platforms generally lack federated public actor IDs, so cross-app identity portability must come from Brehon’s own link flow rather than the chat platform.

### Nostr

Nostr is partial because its relay protocol is intentionally simple and public events are fetchable by clients using relay subscriptions, while user identity is a durable public key rather than a server account ([NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md)). B-fetch can read reported public events from relays, and B-actor can map Nostr public keys to Brehon actor IDs.

B-publish should be advisory or community-scoped rather than authoritative. NIP-56 defines reporting events, and NIP-72 defines moderated communities and moderator actions, but independent relays and clients choose whether to enforce or display those actions ([NIP-56 reports](https://github.com/nostr-protocol/nips/blob/master/56.md), [NIP-72 moderated communities](https://github.com/nostr-protocol/nips/blob/master/72.md)). Brehon can therefore publish signed moderation events, labels, or relay blocklist recommendations, but it cannot guarantee global mute/remove/ban semantics across relays.

### Friendica, Hubzilla, and streams

Friendica, Hubzilla, and streams are partial because they sit in the federated social-web family and can expose ActivityPub-compatible actors and social APIs, but the project-specific B-publish surface is less standardized than PeerTube, Matrix, Discourse, or NodeBB. Friendica documents an API surface, and streams is an open-source federated social-web codebase, but Brehon should validate exact report, block, and local moderation endpoints before ranking them as strong ([Friendica API docs](https://wiki.friendi.ca/docs/api), [streams repository](https://codeberg.org/streams/streams)).

The recommended design is to reuse ActivityPub `Flag` for reports, map actor URLs to Brehon actor IDs, and deploy a local subscriber only on instances that expose a safe plugin/admin action surface. Hubzilla/streams-style identities may also involve Zot/Nomad semantics rather than plain ActivityPub-only identity, so B-actor mapping should store both the local account identifier and any federated actor URL.

### Mobilizon, Funkwhale, and Castopod

Mobilizon is partial but valuable for event-oriented communities. B-fetch can read public event and group data through its GraphQL API and ActivityPub federation, while B-publish would need to map sanctions into group membership, event comment moderation, or event visibility rather than generic social-network bans ([Mobilizon GraphQL API docs](https://docs.mobilizon.org/5.%20Interoperability/3.graphql_api/), [Mobilizon ActivityPub docs](https://docs.mobilizon.org/5.%20Interoperability/1.activity_pub/)).

Funkwhale is partial because its moderator documentation describes pod-level moderation of users, domains, allow-lists, reports, and library content, but the safest Brehon implementation is a local pod extension or service that is validated against the current Funkwhale API and plugin support ([Funkwhale moderator docs](https://docs.funkwhale.audio/moderator/index.html), [Funkwhale federation settings docs](https://docs.funkwhale.audio/develop/administrator/configuration/federation-settings.html)). B-actor can map ActivityPub actors and local Funkwhale users, while sanctions can map to content hide/delete, domain allow/deny, user moderation, or library restrictions.

Castopod is partial-to-limited because it is open-source, self-hostable, and ActivityPub-enabled, but its REST API is disabled by default and primarily automates podcasts and episodes rather than exposing a broad moderation-subscriber surface ([Castopod docs](https://docs.castopod.org/main/en/), [Castopod API overview](https://docs.castopod.org/develop/en/api/)). Brehon can issue ActivityPub-facing advisories or integrate with local Castopod extensions, but Castopod should not be prioritized ahead of PeerTube or Funkwhale for media-community governance.

## Blocked: Keet, Holepunch, Pear, and similar serverless E2EE P2P apps

Keet/Holepunch/Pear-style applications are blocked under the current Brehon contract because B-fetch assumes a reported item can be read from an existing public or app-authorized API at report time. Keet describes every message, call, and file transfer as end-to-end encrypted and directly exchanged between participants, with no servers or third parties involved, which removes the server-side evidence API that Brehon’s hashed-snapshot model expects ([Keet privacy page](https://keet.io/)).

B-publish is also blocked because the Brehon contract assumes the app can run a small subscriber that translates sanction events into local primitives such as mute, remove, restrict, or ban. Pear describes itself as a peer-to-peer runtime and zero-infrastructure development/deployment platform for applications shared and run among peers, not as a community server with a moderation bot, webhook, appservice, or plugin subscriber plane ([Pear documentation](https://docs.pears.com/)).

B-actor is only partial for this class because a P2P app may have cryptographic keys or seed phrases, but those identities do not by themselves create an application-wide governance plane that can enforce cross-user sanctions. The only viable Brehon-compatible route would be a new application-specific moderation protocol designed into the P2P app itself, such as shared signed blocklists that clients voluntarily apply, but that would be a new contract rather than an integration with Keet’s existing public API and subscriber surface.

## Ride existing rails: what Brehon should reuse

### ActivityPub `Flag`, `Block`, `Undo`, and practical federation limits

ActivityPub’s protocol-level object delivery is useful for Brehon because it already defines server-to-server inbox/outbox flows, and ActivityStreams defines verbs including `Flag`, `Block`, and `Undo` that can carry report, block, and reversal semantics ([W3C ActivityPub Recommendation](https://www.w3.org/TR/activitypub/), [W3C ActivityStreams vocabulary](https://www.w3.org/TR/activitystreams-vocabulary/)). Brehon should use `Flag` to federate reports/advisories to ActivityPub instances and should archive B-fetch snapshots locally so that a remote instance can choose whether to trust or ignore the advisory.

In practice, ActivityPub moderation is not a universal remote-control plane. Mastodon documents that incoming `Flag` becomes a moderation report and that outbound remote reports are sent as `Flag` activities from the instance actor, while `Block` can signal that a remote server should hide a profile but is “not guaranteed” ([Mastodon ActivityPub documentation](https://docs.joinmastodon.org/spec/activitypub/)). Therefore, Brehon should treat ActivityPub as a report and advisory rail, while leaving actual suspend/silence/delete decisions to each participating instance’s local subscriber and policy.

### Shared Fediverse safety infrastructure

Brehon should interoperate with shared Fediverse safety services rather than duplicating all trust-data infrastructure. IFTAS provides trust-and-safety resources, moderator community support, denylist resources, and a FediCheck moderation-as-a-service domain federation app that can automatically update Mastodon domain blocks and retractions from trusted lists ([IFTAS Trust & Safety Resources](https://about.iftas.org/trust-safety-services/), [IFTAS Spring 2024 update](https://about.iftas.org/2024/04/23/spring-2023-update/)).

Fediseer is relevant because it offers a FOSS REST API for Fediverse instance reputation, guarantees, endorsements, and anti-spam verification, which Brehon could consume as prior reputation evidence or publish to as a community trust signal ([Fediseer site](https://fediseer.com/), [Fediseer repository](https://github.com/Fediseer/fediseer)). The Bad Space is relevant as an example of composite shared blocklist infrastructure because it describes a public API and CSV outputs derived from current-source instance blocklists, although Brehon should treat third-party blocklists as advisory inputs subject to community policy rather than automatic sanctions ([The Bad Space about page](https://tweaking.thebad.space/about), [IFTAS statement on third-party denylists](https://about.iftas.org/2025/04/08/statement-on-iftas-ethical-commitments-community-relationships/)).

### Bluesky labelers and Ozone

Brehon should reuse Bluesky’s labeler model directly for AT Protocol integrations. Bluesky’s docs describe moderation as stackable systems including network takedowns, labels from moderation services, and user controls, and they explain that labelers can publish labels on accounts or records for clients to hide, warn, or ignore ([Bluesky labels and moderation docs](https://docs.bsky.app/docs/advanced-guides/moderation)).

Ozone is a concrete implementation path because Bluesky describes it as open-source labeler tooling that can field reports and publish labels, and the architecture documentation lists the labeler endpoints `com.atproto.label.subscribeLabels`, `com.atproto.label.queryLabels`, and `com.atproto.report.createReport` ([Bluesky moderation architecture blog](https://docs.bsky.app/blog/blueskys-moderation-architecture), [Ozone repository](https://github.com/bluesky-social/ozone)). Brehon’s initial AT Protocol integration should therefore be a Brehon labeler plus optional Ozone-compatible moderation queue import/export, not a custom account-suspension system.

## Implementation recommendations

First, prioritize **Discourse, NodeBB, and Bluesky labelers** as additional app planes after PeerTube because each offers a documented, non-invasive subscriber model and a clear user/content identity scheme. Discourse and NodeBB cover long-form forums, while Bluesky labelers give Brehon a standards-aligned moderation-service pattern that is close to Brehon’s “one jury pool, many app planes” goal ([Discourse API docs](https://docs.discourse.org/), [NodeBB plugin docs](https://docs.nodebb.org/development/plugins/), [Bluesky labels and moderation docs](https://docs.bsky.app/docs/advanced-guides/moderation)).

Second, implement ActivityPub microblogging as **Partial by design**, not as a hard-enforcement target. The correct product shape is “Brehon emits report/advisory/sanction events; each Mastodon/GoToSocial/Pleroma/Akkoma instance runs a local subscriber that chooses how to apply them,” because the documented admin APIs require local moderator authority and ActivityPub `Block` is not guaranteed remotely ([Mastodon admin account action API](https://docs.joinmastodon.org/methods/admin/accounts/), [Mastodon ActivityPub documentation](https://docs.joinmastodon.org/spec/activitypub/)).

Third, for chat systems, standardize an **evidence-visibility policy** before writing more adapters. Matrix can be strong in non-E2EE governed rooms with an appservice, while Mattermost, Rocket.Chat, and Zulip are partial because B-fetch depends on channel membership and B-publish depends on workspace-local privileges ([Matrix Application Service API](https://spec.matrix.org/latest/application-service-api/), [Mattermost server plugin SDK](https://developers.mattermost.com/integrate/reference/server/server-reference/), [Rocket.Chat Apps-Engine overview](https://developer.rocket.chat/docs/rocketchat-apps-engine), [Zulip event queue API](https://zulip.com/api/register-queue)).

Fourth, keep Nostr and P2P networks out of the hard-enforcement roadmap. Nostr can consume and publish signed moderation advisories because NIP-56 and NIP-72 define report and moderated-community event patterns, but relays and clients remain the enforcement points ([NIP-56 reports](https://github.com/nostr-protocol/nips/blob/master/56.md), [NIP-72 moderated communities](https://github.com/nostr-protocol/nips/blob/master/72.md)). Keet/Holepunch/Pear should stay blocked until those apps expose a public evidence API and an enforceable subscriber/label protocol compatible with Brehon’s thin contract ([Keet privacy page](https://keet.io/), [Pear documentation](https://docs.pears.com/)).

## Bottom line

The most realistic expansion path is: **PeerTube next; then Discourse, NodeBB, and Bluesky labelers; then ActivityPub microblogging as local-subscriber/advisory integration; then selected team-chat systems with explicit private-room constraints; then long-tail Fediverse apps where local plugin surfaces exist**. Brehon should not attempt to become an identity provider, admin console, or universal delete button; its durable advantage is a portable actor/reputation/jury layer that publishes verifiable community sanctions into app-local enforcement surfaces and existing federation moderation rails.
