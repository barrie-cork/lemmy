When an advisor session drives a long-running pipeline via repeated `ScheduleWakeup` self-prompts, **do not pack the full verbatim decision-tree into the wakeup `prompt` field**. The decision-tree describes the *expected* next stage; the moment a stage actually completes (often during the very wait the wakeup was scheduled for, via a background-task notification or a faster-than-expected Junior), the next wakeup fires carrying a now-stale prompt that re-describes already-done work. The session must then recognise the staleness by checking live state — which means the verbose prompt payload was pure cost: ~2-4k stale-context tokens re-read on every post-completion re-entry, for zero signal.

Confirmed: v1-ship-1-r2, 2026-05-18. The advisor scheduled wakeups with long verbatim decision-trees ("IF Phase-2 e2e PASS → mutate DQ #264 → /brehon-verify → bm-pr → ... IF FAIL → §G4 ..."). Stages completed faster than the wakeup cadence (background e2e notification fired; Junior tasks finished early). At least **4 separate wakeup re-invocations** fired carrying prompts describing the Phase-2 e2e run, the retro, or the phase-transition — all of which prior turns had already completed. Each was correctly recognised as stale *only because the session checked live state first* (`TaskList` + DQ pending + `gh pr view`) and saw the work was done. The recognition worked every time; the verbose prompt that triggered the need for recognition was the waste.

**How to apply:**

- A `ScheduleWakeup` prompt for a long-poll resume should be **one or two lines**, not a decision-tree:

  > `Resume v1-ship-1-r2 orchestration at expected stage <X> (e.g. "Phase-2 e2e on merged tip / bm-merge poll"). FIRST verify live state — `mcp__junior-brehon__list_tasks`, DQ pending, `gh pr view <N>` — and act on what is ACTUALLY true now, NOT on this prompt's assumptions (the stage may have completed since this was scheduled). If already done, advance to the next real stage.`

- The detailed routing logic (the IF/THEN tree, the §G4 classifier path, the gate sequence) **lives in the rules/skill** (`advisor-orchestrator.md`, `auto-phase.md`), not re-pasted into every wakeup. The session reads the rule when it actually needs the branch, not pre-loaded into a prompt that may be stale before it fires.
- Make the **live-state-check-first discipline explicit in the prompt** rather than implicit. It is already the de-facto guard (the session does it anyway and catches the staleness); stating it in the thin prompt makes the guard a named step instead of a lucky habit, and removes the incentive to pack the prompt with "just in case" detail.
- The wakeup prompt's job is **"when to wake + what stage to resume at"**, not **"what to do in every branch"**. The runtime resolves the latter from live state + the canonical rules at fire time.
- Token arithmetic: a verbose decision-tree prompt is ~2-4k tokens; re-read on every post-completion wakeup re-entry across a multi-hour long-poll, that's tens of k of displaced reasoning headroom for a session whose context is already long. A thin prompt is ~100 tokens and the rule-read (only when a branch is actually needed) is paid once, on demand.

**Generalises to:** any agent that schedules its own future wake-ups to drive an asynchronous pipeline (long-poll orchestration, CI-watch, deploy-watch). The scheduled prompt is written *before* the awaited work resolves, so any decision logic baked into it is speculative and decays the instant the state changes. The durable form is: thin prompt = wake trigger + resume-stage pointer; decision logic = read live state + canonical rule at fire time. Same family as `feedback_pre_phase_dod_smoke_test.md` (act on verified current reality, not a prior assumption) and the standard "trust-but-verify the real state, never the stale self-report" discipline in `feedback_bm_false_success_advisor_post_condition_catch.md`.
