name: Advisor must dry-run a transcribed process-rule's branch/file preconditions against current state before committing the brief
description: When an advisor transcribes a multi-step git/process rule into a brief OR executes a multi-step plan from a handover, the advisor must first verify preconditions against current state (file/branch divergence, self-declared loading discipline of any target file, existence of every named path). Brief-author-time / pre-mutation checks cost seconds; execution-time failures cost full cycles. Generalises the L14 self-conflict + context-prune Option B handover-execution incidents.
type: feedback
---

When an advisor authors a brief that **transcribes a documented multi-step git/process rule** into a Junior's §4 Constraints, the advisor must first **dry-run the rule's branch-topology and file-touch preconditions against the actual current sub-phase state** — specifically: *does any earlier step already executed in this sub-phase touch the same file or branch this rule is about to mutate?* If yes, the rule may self-conflict, and faithfully transcribing it into the brief ships the conflict to execution time.

The failure mode is **not** a Junior going off-script. It is an advisor brief that correctly implements a rule whose preconditions the current state already violates. Brief-authoring *feels* low-risk ("just transcribe the documented sequence") — which is exactly why this slips.

Confirmed: v1-ship-1-r2, 2026-05-18. The L14 fix is a documented rule: the bm-merge BM commits a `## bm: merge` entry to `.claude/runlog/bm-runlog.md` on `governance-v0`, then `git push`, then `gh pr merge`. The advisor transcribed this verbatim into the first bm-merge brief. But an **earlier step in the same sub-phase** — bm-pr — had *already* appended a `## bm: PR opened` entry to the *same file* on the *phase branch* (commit `d0e52fdb4`). Both branches therefore diverged on `bm-runlog.md` from their common ancestor → `gh pr merge` failed `mergeStateStatus: DIRTY / CONFLICTING` → Junior #322 BLOCKED. Cost: a full failed bm-merge cycle + ~30 min advisor inline conflict-resolution + a re-dispatch (Junior #323). A 30-second check at brief-author time — "L14 writes `bm-runlog.md` on trunk; did anything earlier in this sub-phase write `bm-runlog.md` on the phase branch? — yes, bm-pr did" — would have caught it before the brief was committed. See `feedback_l14_runlog_on_trunk_self_conflicts_with_bm_pr.md` (the L14-specific fix) and DQ #265; this lesson is the **generalisation** of that incident to all transcribed process rules.

Confirmed (2nd, broader scope): context-prune Option B Steps 1+2, 2026-05-22. The handover at `.claude/PRPs/handovers/context-prune-option-b-2026-05-22.md` proposed relocating `auto-phase.md` + `auto-roadmap.md` from `.claude/rules/` (auto-loaded at session start) to `.claude/refs/` (lazy-load only). Same underlying principle as the L14 incident — verify preconditions of a documented plan against current state before executing — but the scope is wider: any execution-time read of a documented procedure (handover, plan, transcribed rule) by an orchestrator.

**How to apply:**

- When a brief's §4 Constraints transcribes a multi-step git/process sequence (L14, L15, L16, any `bm-*` ordered sequence, any rule that says "commit X to branch Y BEFORE action Z"), run a **precondition dry-run before `git add` of the brief**:
  1. List every *file* and *branch* the rule mutates (e.g. "L14: writes `.claude/runlog/bm-runlog.md` on `governance-v0`, then merges `<phase>` into `governance-v0`").
  2. For each, ask: *has any earlier step in THIS sub-phase already written that file on a branch that will be merged here, or already mutated that branch in a way that diverges?* Use `git log <phase-branch> --oneline -- <file>` vs `git log governance-v0 --oneline -- <file>` to make divergence visible in one command.
  3. If a divergence is possible → the rule self-conflicts in this context. Do NOT transcribe it as-is. Either adjust the brief (e.g. move the conflicting write post-merge, as the L14 revision did) or surface the rule defect to the user before dispatch.
- This is a **brief-author-time gate**, cheap (one or two `git log -- <file>` calls + 30 seconds of reasoning). The alternative (catching it at `gh pr merge` time) costs a failed Junior cycle + inline recovery + re-dispatch.
- Most-likely-to-bite rule shapes: any "commit to trunk BEFORE merge" ordering on an append-only shared file (runlog, decision-queue, a manifest) that an *earlier* phase step also appended to on the feature branch. The structural fix for the append-only-file sub-case is a `merge=union` `.gitattributes` driver (shipped for `bm-runlog.md`); but the *general* discipline is the brief-author-time precondition dry-run, because not every transcribed rule is about an append-only file.
- **Read the target file's own preamble before relocating it.** Self-declarations of loading discipline are load-bearing invariants — relocations must preserve them via consumer hardening (lazy-load `Read` in the consuming skill body) OR explicitly update the self-declaration in the same commit. Check: open the file, grep for "session start", "always-loaded", "auto-loaded", "read at session start", "loaded once"; if present and the move defeats the claim → adjust the move plan or surface to user via AskUserQuestion. Confirmed: context-prune Option B Step 2 (2026-05-22, ship commits `f4d584345` + `17a3eb1bb`); the rule files' preambles self-declared "read at session start" and the handover at `.claude/PRPs/handovers/context-prune-option-b-2026-05-22.md` would have defeated that invariant silently — caught only by re-reading the preambles before `git mv`. Full retro at `.claude/PRPs/reports/session-retro-2026-05-22-context-prune-option-b-steps1-2.md`.
- **Inventory the path list against the filesystem before trusting a handover.** Handover authors work from a mental model that may be stale (renames, typos, scope-creep notes that didn't ship). Check: `Glob` or `ls` every path the handover names BEFORE any mutation; surface non-existent paths to the user before proceeding. Confirmed: context-prune Option B Step 2 (2026-05-22) — the handover named `~/.claude/commands/auto-roadmap.md` as an edit target but only project-scope `.claude/commands/auto-roadmap.md` exists; user/project-scope `roadmap-next.md` are also different files, not symlinks (`diff -u` shows materially different content). See retro at `.claude/PRPs/reports/session-retro-2026-05-22-context-prune-option-b-steps1-2.md`.
- **Audit consuming-file semantics-claims, not just citation paths.** A relocation often invalidates documentation IN CONSUMING FILES that asserts loading semantics (e.g. "the rule is sticky for the session" becomes false when the rule lazy-loads per-invocation). Check: after listing every file that cites the relocation target, also grep within those files for semantics-claims ("sticky", "auto-loaded", "loaded once", "session start", "until restart"); update each to reflect the new loading reality in the same commit. Confirmed: context-prune Option B Step 2 (2026-05-22, ship `17a3eb1bb`) — user-scope `auto-phase.md` §6 "Mid-phase skill-edit deferred-effect awareness" asserted rule files are "sticky for the session"; that became false when the rule moved to `.claude/refs/` and now reads per-invocation. Retro at `.claude/PRPs/reports/session-retro-2026-05-22-context-prune-option-b-steps1-2.md`.
- Candidate home for the gate: `.claude/rules/advisor-orchestrator.md` §2 (Brief authoring) — one line: "Before committing a brief that transcribes a multi-step git/process rule, dry-run the rule's file/branch preconditions against current sub-phase state (`git log <phase> -- <file>` vs trunk); a rule whose preconditions the current state already violates must be adjusted or surfaced, not transcribed as-is. Per `feedback_advisor_dryrun_process_rule_preconditions_at_brief_author.md`."

**Generalises to:** any orchestrator that mechanically transcribes a documented multi-step rule into a worker instruction. A rule is correct *in the abstract* but its preconditions are *context-dependent*; the orchestrator is the only actor positioned to check the preconditions against current state, and "the rule is documented, just transcribe it" is the precise mental shortcut that skips that check. The check is always cheaper at authoring time than at execution time. Same family as `feedback_bm_false_success_advisor_post_condition_catch.md` (the orchestrator's independent check is the load-bearing safeguard) and `feedback_pre_phase_dod_smoke_test.md` (dry-run the commands/rule against reality before relying on them). The three 2026-05-22 sub-patterns extend this to any execution-time read of a documented procedure — a handover, a plan, or a transcribed rule — where the orchestrator's pre-mutation check against current state (target-file self-declarations, filesystem inventory, consumer semantics-claims) is the only thing standing between a documented hypothesis and a costly execution-time failure.
