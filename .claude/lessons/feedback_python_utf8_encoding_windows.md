On Windows, Python's `open()` defaults to `cp1252` encoding (system ANSI
codepage), not UTF-8. Reading a UTF-8 JSON file and writing it back
without specifying `encoding="utf-8"` silently re-encodes non-ASCII
characters as mojibake: `§` becomes `Â§`, `—` becomes `â€"`, `€`
becomes `â‚¬`.

The corruption is silent — no exception raised, no warning emitted.
`git diff` exposes it only because the bytes differ from the committed
UTF-8 version.

**How to apply:**

When editing JSON or any UTF-8 file via Python on Windows, **always**
pass `encoding="utf-8"` to both read and write:

```python
# Correct
with open(".claude/decision-queue.json", encoding="utf-8") as f:
    q = json.load(f)
# ... modify q ...
with open(".claude/decision-queue.json", "w", encoding="utf-8") as f:
    json.dump(q, f, indent=2, ensure_ascii=False)
```

Note also `ensure_ascii=False` on `json.dump` — the default escapes
non-ASCII to `\uXXXX`, which mangles visual readability of already-valid
UTF-8 content even if the bytes are correct.

**Caught it pre-commit 2026-04-19** during PR #46 review response when a
Python-scripted decision-queue entry round-trip corrupted every `§` and
`—` in prior entries. Reverted via `git checkout --` before the bad
bytes landed. See `project_pr46_phase_6_review_response.md`.

This applies to:
- `.claude/decision-queue.json`
- `.claude/task-hopper.json`
- Any YAML/markdown file in the project that uses `§`, `—`, `✅`, `🔴`, etc.
- Any JSON file generated by a tool and round-tripped through Python

When in doubt, use the Edit tool (which is UTF-8-safe) rather than a
Python script.
