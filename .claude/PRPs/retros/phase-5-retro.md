# Phase 5 retro — reputation, sponsorship, adaptive governance

**Scope:** covers Phase 5a (config infra + reputation snapshot + endorsement — tasks 50–55, 6 tasks), Phase 5b (sponsor-liability + jury gating + founder CLI — tasks 56–60, 5 tasks), Phase 5c (remaining endpoints + observability + V2 hooks — tasks 61–70 + 69a, 11 tasks). Shipped 2026-04-17 (5a), 2026-04-18 (5b), 2026-04-19 (5c). governance-v0 HEAD at Phase 5 close: `156db7cc8` (PR #10 merge commit).

## What surprised us

- **The `--features full` + `-p <crate>` incompatibility recurred three times across sub-phases** (5a task 0, 5b DQ #15, 5c DQ #14) before being promoted to `feedback_features_full_p_crate_incompatible.md`. The plan-review pass should catch this class at plan-write time, not defer to impl-time fixup. Auto-promotion at 3× is the RLS working as intended, but the ideal outcome would have been catching it at 5b.
- **pq-sys wrapper env poisoning had a second trigger** distinct from the Phase 0 install-after-build case. `cargo-check.bat` didn't set `PQ_LIB_DIR`, `cargo-test.bat` did — running check first poisoned the pq-sys build cache for the subsequent test run. Fixed by adding `PQ_LIB_DIR` block to cargo-check.bat + cargo-clippy.bat in 5c. The existing feedback memory was updated with the second-trigger section.
- **The tokio-postgres 0.7.16 notification API was worse than the plan anticipated.** Plan §11.10 69a.3 snippet assumed `client.notifications().next()` — that method doesn't exist at this version. DQ #20 pre-seeded this correctly but the impl still spiralled for ~5 exploration rounds before the advisor directive with the authoritative `poll_message` + `poll_fn` + mpsc bridge pattern ended the cycle. Lesson: pre-seeded DQ answers must be paired with a concrete code snippet, not just an API shape description.
- **A real production bug was discovered at task 70 close, not during task 53 when the code was written.** `acquire_advisory_xact_lock` used `.load::<IgnoredRow>()` against `pg_advisory_xact_lock()` which returns `void`, causing runtime "Received less than 8 bytes while decoding an i64." The bug shipped through Phase 5a, 5b, and most of 5c because no prior test actually ran the advisory lock path — task 69's 3-branch capability test was the first exercise. This validates Watch 4 + Watch 9 as genuinely load-bearing, but also reveals that snapshot concurrency tests should have landed earlier.
- **Fresh test users failed `jury.age_requirement_days` = 60 default.** Task 69 test fixtures ran `run_snapshot_batch` then asserted jury eligibility — but fresh users are seconds old, so the snapshot computed `jury_eligible = false` for everyone, triggering fallback to random pick. Fixed by inserting a `governance_config` override row for `jury.age_requirement_days=0` before the snapshot run. Test-fixture config overrides are a real v0 pattern that the plan didn't anticipate.
- **DQ #27 (upstream rebase mid-phase) resolved cleanly.** The advisor pre-seed with advisor-answered Option (a) meant the impl executed the rebase with zero conflicts at the Slice A/B boundary. 17 commits ahead, 0 behind after rebase. No Rust 1.95 fallout surfaced post-rebase. Pattern worth repeating for Phase 6.
- **Force-push-with-lease worked cleanly** at the Slice B close. The impl stopped to ask (correct per `feedback_advisor_instruction_mismatch_stop_and_ask.md`) even though DQ #27 explicitly authorised the rebase. The handshake preserved audit trail without costing momentum.
- **Auto-mode impl agents work for Slice B-style execution.** Slice B tasks 68–70 ran in auto mode with advisor monitoring via 3-minute polling loop. Zero catch-fires. The impl correctly flagged the force-push question, resolved the advisory lock bug independently, and handled the age_requirement_days fixture fix without advisor intervention.

## What to change

- **Plan-review pass must include a "features × scope" compatibility grep.** Every DoD command that combines `-p <crate>` with `--features full` is a known failure. The plan agent should auto-flag these at plan-write time. Candidate: add to `feedback_plan_dod_dry_run_at_write.md` or spawn a dedicated plan-lint memory.
- **Pre-seeded DQ answers for API-specific questions must include concrete code snippets, not just API shape descriptions.** DQ #20 correctly identified the poll-based pattern but didn't ship the bridge code. The impl spent iterations re-deriving the snippet. For Phase 6, DQ pre-seeds for `activitypub_federation` trait impls should include working code templates.
- **Concurrency tests should land in the phase that introduces the concurrency primitive.** `pg_advisory_xact_lock` was added in Phase 5a task 53 but not actually exercised until 5c task 69. If a pair of concurrent recomputes had been tested in 5a's e2e, the void-return bug would have surfaced 2 weeks earlier. For Phase 6: the federation outbound publisher's queue behaviour should have a concurrency test in the same phase.
- **Test fixtures that set up reputation-driven state must include config overrides for temporal gates.** Every Phase 6 test that seeds users and expects them to be jury-eligible / federation-eligible / sponsor-eligible must override `jury.age_requirement_days`, `onboarding.sponsor_min_account_age_days`, and any other day-count gates to 0 before `run_snapshot_batch`. Add this as a test-fixture helper in a carry-forward.
- **Retro must be written before phase-close PR merge, not after.** This retro was written post-merge, which means the phase transition skill's retro gate correctly blocked the handoff but delayed the Phase 6 kickoff. For Phase 6: write the retro as part of task 77 or 78 DoD, not after PR merge.
- **CodeRabbit false-positive ADR flags** should be expected as advisory, not blocking. The three red flags on PR #10 (governance_log DROP TRIGGER in migration down.sql, grep match inside markdown, keycloak word in V2 research doc) were all false positives. The current workflow was advisory-only, which was correct. Don't tighten this to blocking without a regex refinement pass.

## What to carry forward

- **3-way sub-phase split for high-reasoning domains** (Option C from the design-soundness review) worked well for Phase 5. 5a infra, 5b math, 5c endpoints — isolated review surface per sub-phase, clear dependency order. Phase 6 has cleaner boundaries and may not need a split, but the pattern is proven for any future phase with similar reasoning density.
- **Decision-queue pre-seeding at phase start** reduced mid-loop friction materially. Five advisor pre-seeds (#22–#26) + one advisor-answered mid-phase entry (#27) all landed cleanly. The impl's task 0 sweep absorbs pre-seeded entries into `resolved[]`. Keep this pattern.
- **Session split at ~200k used context** is load-bearing. Phase 5a retro established the rule; Phase 5c honoured it (session 1 closed after task 63, session 2 opened at task 64). The model-window size (1M) doesn't change the 200k reasoning-degradation threshold.
- **`/advisor-checkpoint` at session-close** preserves state across swap boundaries. Both the Slice A close and Slice B open benefited from the checkpoint block format in `project_brehon_phase_5_notes.md`.
- **Force-push-with-lease for feature branches after rebase** is safe when DQ explicitly authorises and no other consumer exists. Phase 6 PR close may need the same pattern if it absorbs an upstream rebase.
- **`--merge` not squash at PR close** preserves the one-commit-per-task chain for CodeRabbit's per-commit review surface and for historical traceability. Phase 5b's squash-merge orphaned 4 commits — Watch 5 discipline prevented a repeat in 5c.
- **Move-3 flip-verification sequence** (task 64's Accepted→Selected flip) prevented a broken-test-edit masking the flip. Template for any future phase mutation of a Phase 4 handler: write the test against pre-change behaviour first, verify it passes, then flip the code, verify the test fails as expected, then fix the test. Documented in commit body, not just plan text.
- **Advisor monitoring via 3-minute polling loop** scaled well for auto-mode Slice B. The advisor arms `ScheduleWakeup`, polls git log + decision-queue + ralph state, reports only anomalies. Silent-when-nothing-changed discipline kept the pattern low-noise. Carry forward for Phase 6 layer orchestration.
- **V2 messaging hooks reserved in task 69a** are a good pattern for future-proofing. The NOTIFY trigger + SUBSCRIPTIONS.md contract + underscore-username regression test cost ~200 LOC for hooks that unblock V2 phases without v0 scope creep. Apply the same "reserve now, build later" discipline in Phase 6 for federation inbox hooks that will matter at v1.
- **Pre-phase harness audit (task 0)** catches wrapper drift + feature-flag mismatches before they cost iterations. Run it at every Phase 6 layer boundary, not just phase start, since Phase 6 introduces new crates (`apub/objects`, `apub/activities`, `apub/apub`).
- **Auto-promotion to feedback memory at 3× occurrence** works. The `--features full` / `-p <crate>` class hit 3× before promotion; now it's durable. Keep the 3× threshold; don't prematurely promote at 2× (single recurrence can be coincidence).
- **Watch 11 admin-config-write.sh pattern** (action-time modlog entry for every admin config mutation) is the Brehon self-enforcement principle operationalised. For Phase 6, every federation outbound send + remote inbound receive must emit a governance_log entry at action time, not be inferred from downstream state.
