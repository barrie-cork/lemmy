# v1-AD-a retro — admin-dashboard foundation

v1-AD-a is the first v1 sub-phase to ship via `/prp-ralph` on a phase-`<N>` branch with a PR flow. Tasks 1–9 were pure SCHEMA + CONFIG + METADATA — no HTTP handlers, no business logic, no plugin hooks — and that narrow scope is mostly why the loop converged cleanly. This retro covers both the loop mechanics and the implementation itself.

## What worked

- **Atomic task-per-commit discipline held end-to-end.** Every plan task produced exactly one commit with the subject line `feat(v1-AD-a): task N — …` or `docs(v1-AD-a): task N — …`. Task 5's correction was a 10th commit (`fix(v1-AD-a): task 5 gap — …`) rather than an amend — preserved the review-history shape per `phase-branch.md` "Do not squash" rule. CodeRabbit and the human reviewer can read each task's delta in isolation.
- **Compile-time parity test caught the 27-key reconciliation drift at write-time, not at migration-run-time.** The `every_seeded_key_has_metadata` test in `config.rs` fired the instant `SEEDED_KEYS_WITH_CONSTS.len()` didn't equal `CONFIG_KEY_METADATA.len()` — so if task 6's 61-entry metadata array had missed or double-counted a key vs task 7's 27-row INSERT, clippy+lib-test would have rejected the commit. Four parallel edits (seed SQL, `SEEDED_KEYS_WITH_CONSTS`, `const_default_*` match arm, `CONFIG_KEY_METADATA` entry) is error-prone; the parametric parity assertion converted that error-proneness into a test-time signal.
- **Advisor edit #1's "PRD §5.2 is source of truth" pre-empted plan-vs-PRD drift.** Plan §13 task 6 enumerated 27 keys but omitted the 2 `governance.dashboard.*` keys and over-counted `rule_set.*` (4 instead of 3). The reconciled list lives in the state file under Codebase Patterns — "Authoritative 27-key v1-AD-a list is from PRD §5.2 minus 10 sponsor-liability rows minus `rule_set.active_version_id` — NOT from plan §13 task 6/7 sample lists." That saved me from copy-pasting the wrong list into task 6 or task 7 and having the parity test rediscover it downstream.
- **Dual-file edit for `governance_log.rs` entry-kind consts landed atomically (task 7).** Post-Phase-6 the canonical definition moved to `lemmy_db_schema::source::governance::governance_log` while the API shim at `crates/api/api/src/governance/governance_log.rs` became a re-export. Task 7 edited both in a single commit. A split would have made either file temporarily broken in isolation; the commit-level atomicity matched the "both files are one logical edit" semantics.
- **Captured cargo output to files and tailed them, never piped.** Zero exit-code surprises — every `cargo-check.bat` and `cargo-clippy.bat` exit status was captured via same-shell `STATUS=$?`, not a second bash line. `.claude/rules/cargo-output-capture.md` held.
- **Plan §15's Level 5 `--no-deps --features full -- -D warnings` was a correctly-scoped clippy gate.** Strict but narrow. Zero warnings, zero errors on v1-AD-a-touched code.

## What surprised us

- **`cargo check --workspace --features full` passes a 16-field Queryable struct against an 18-column table.** The Queryable derive generates one impl per struct shape; no caller requested the 18-col Queryable bound from library code, so nothing exercised the mismatch. The test harness at `crates/server/tests/e2e.rs` uses `.get_result(conn)` on `moderation_case::table` — which DOES require `Queryable<18-col>` — but test targets are not compiled by `cargo check --workspace`. The bug was only visible under `cargo test --test e2e --no-run` or `cargo clippy --all-targets`. Plan §15 Level 4's test-target `--no-run` compile should have fired per-task; instead it was listed as "skip if no Postgres" and got skipped. Root cause: misunderstanding that `--no-run` is a compile-time gate, not a DB-runtime gate. Filed as carry-forward #1 below.
- **Background cargo processes raced with in-flight commits and produced a false-red parity event.** Iteration 4 left a background `cargo-test.bat --workspace --lib parity` running while iteration 5 committed tasks 6 and 7. When the parity cargo got to the `lemmy_api` shim compile, it saw the post-edit shim (`pub use ENTRY_KIND_ADMIN_CONFIG_CHANGED`) but a pre-edit db_schema (without the const definition). Classic TOCTOU: the file-system snapshot each crate's compile uses is not transactionally consistent with the other crates when edits land mid-flight. The "error" wasn't real — a fresh cargo run on the committed tip passed cleanly. But it cost me ~5 minutes of diagnosis and a monitor restart. **Learning: if a background cargo is live, wait for it to exit before committing OR re-run cleanly after the commit lands. Don't try to interpret its output.**
- **The 10th (fix) commit means "9 commits ahead" acceptance criterion is mildly broken.** Plan §16 row 2 says "Branch is exactly 9 commits ahead of `governance-v0` (one per task; task 0 produces no commit)." The fix commit pushes it to 10 (then 11 including the archive). This is a legitimate task-5 correction, but it's technically a criterion miss. I'd reword future plans as "One commit per task; corrections land as additional commits and count toward the total." Filed as carry-forward #2.
- **Clippy `--all-targets` surfaced 100 pre-existing upstream/prior-phase lint violations in `tests/e2e.rs` and `reputation_snapshot.rs`.** The fork's GH Actions CI runs only `cargo-test-e2e`, `adr-compliance`, `adr-drift`, `plan-drift`, `oq-sweep`, and `governance-ai-review` — **no clippy job at all**. The strict clippy step in `.woodpecker.yml` isn't integrated with GitHub on this fork. So this lint debt has been accumulating since Phase 1 without anyone noticing. The stop-hook's `cargo clippy --workspace --all-targets -- -D warnings` would have been a valid gate for v1-AD-a if the baseline at `governance-v0` tip passed it — but it doesn't. I marked it as "not plan DoD; use Level 5 as equivalent" and moved on. **But that debt exists** and will bite the next phase that tries to run `--all-targets` cleanly. Filed as carry-forward #3.
- **Task 5 ships a dead-code crate pattern that's intentional.** `SponsorAllowlistInsertForm` has zero production callers in v1-AD-a — it's reserved for v1-AD-b. Plan §13 task 5 GOTCHA explicitly says "A `#[allow(dead_code)]` is NOT needed if the struct is `pub` and exported — exported items are never dead." The `pub` keyword carries the intent. Nice touch — I'd have reflexively added an `#[allow]` without the GOTCHA.
- **`cargo fmt --all -- --check` emits 648 diffs on stable and zero on nightly.** The `.woodpecker.yml` runs `cargo +nightly fmt --check` explicitly. The `rustfmt.toml` uses nightly-only features (`wrap_comments`, `imports_layout = HorizontalVertical`, `group_imports = One`) that silently no-op on stable. On a solo-dev Windows machine without nightly installed, `cargo fmt --check` is misleading: it reports real-looking diffs that would be no-ops after a nightly run. Noted in stop-hook supplementary; not a plan gate.

## Carry-forward

- **Add a per-task `cargo test --test e2e --no-run -p lemmy_server` gate to future phase plans.** Currently buried in §15 Level 4 "run after build" — should be a per-task validate alongside `cargo-check.bat`. Catches struct-vs-schema drift that `cargo check --workspace` misses (task 5 class of bug). Cost: 10 min cold compile once per phase; every task thereafter is warm-cache fast. Propose as `pre-phase-harness-audit.md` §4 "Test-target compile gate" or a new rule file. **Filed for next phase plan.**
- **Explicitly allow the "corrections land as additional commits" pattern in plan §16 acceptance criteria.** The "exactly N commits" rule is brittle; fix commits are a normal part of any non-trivial phase. Wording change only.
- **File a separate PR to clear the pre-existing `cargo clippy --all-targets` debt in test-target code.** 100 errors in `tests/e2e.rs` + `reputation_snapshot.rs` (mostly `tests_outside_test_module` on `#[tokio::test]`, `indexing_slicing`, `items_after_statements`, `expect_used`). Workspace lint config in `Cargo.toml` declares these as deny, and `.woodpecker.yml` enforces them, but GH Actions on this fork does not. Clearing them would let a future `--all-targets` gate actually work. Estimated 200–400 LOC of test-code tidy-ups, no semantic changes. Label as `polish-N-clippy-alltargets-baseline`. **Blocks nothing; quality-of-life.**
- **Add a stop-hook readable check for "state file gone" race.** When the hook recreates the state file on `iteration++`, it doesn't check whether an intervening assistant message emitted `<promise>COMPLETE</promise>` before the transcript flushed. A second promise-emission was needed this iteration. A 500ms `sleep` in the hook before reading the transcript would avoid it. **Not v1-AD-a's responsibility; filed as a harness improvement.**
- **Add the post-Phase-6 canonical location of `governance_log` consts (+ the shim pattern) to `CLAUDE.md` or a new rule.** The DQ-6.6-inbound resolution moved the definition down to `lemmy_db_schema` and left a shim at `crates/api/api/src/governance/governance_log.rs`. Every future phase that adds an `ENTRY_KIND_*` must edit both files atomically in the same commit. Task 7's dual-file edit worked because I happened to read the plan's §10.8 cross-reference carefully; a future implementer without that context would edit the wrong file first. Propose: `.claude/rules/governance-log-dual-file-edit.md`. **Not blocking.**
- **Harness: `cargo fmt` on stable is not a meaningful gate; either install nightly in the wrapper or suppress fmt in the stop-hook supplementary when no nightly is detected.** Currently the stop-hook lists fmt as a required command, which was noise in both my completion reports. Either make it work or drop it. **Filed as harness improvement.**
- **Plan-vs-PRD drift is a real class.** Task 6 GOTCHA enumerated 27 keys but was wrong (advisor edit #1 source-of-truth correction). A plan that re-enumerates data also owned by a PRD will drift; solution is to reference the PRD by section anchor and let the implementer reconcile at write-time, NOT to duplicate the list in the plan body. Noted for future `/prp-plan` outputs.
