# m3-core-recording — planning brief

`[role:planning]` Author the M3 Phase-5 plan: **optional evidentiary-store recording** for town-hall rooms, gated on `record_town_halls=true` (default false). LiveKit Egress → MP4 → MinIO (generic S3 API) → `content_sha256` → callback into the binary's `append_room_event()` for the FIRST `room_recording_uploaded` chain emission. Participant-floor authorization on fetch (ADR-015 pin). A `record_town_halls=false` town hall must produce ZERO recording side-effects. Bridge-side only; Linux-compile only.

## 4. Constraints (enforce in the plan)

- **`content_sha256` rides `append_room_event`, NEVER a raw digest (CATCH-FIRE-CLASS, LOAD-BEARING).** The recording's `content_sha256` is a tamper-evidence hash on the governance chain (OQ-V2-04 resolution: "tamper-evidenced by design"). It MUST flow through `append_room_event` (`crates/api/api/src/governance/governance_log.rs:238`), which runs `scrub_json` + the ed25519 hash-chain + signing. A `room_recording_uploaded` emission whose `content_sha256` is computed and written via a bare `sha2::Sha256::digest` call that bypasses the chain append path is an ADR-008/ADR-016 violation — catch-fire (bootstrap §7 + tripwire). Gate the planner must encode: §16a story asserts the `content_sha256` appears in the `governance_log` chain row, with a valid signature/prev-hash link — not merely in a local variable. (Computing the SHA256 of the MP4 bytes with `sha2` is fine — the CONSTRAINT is that the hash reaches the chain via `append_room_event`, not via a side channel.)

- **`record_town_halls=false` produces ZERO recording side-effects (HARD DoD INVARIANT, LOAD-BEARING).** A town hall with the flag off must run normally with no Egress trigger, no MinIO write, no `room_recording_uploaded` chain entry (Success Criteria line 145 + bootstrap §7 + tripwire). The §16a clean-posture story MUST assert the NEGATIVE: enumerate the recording side-effects (Egress call, S3 PUT, chain entry) and assert NONE occur. Mechanical check (per `feedback_authz_state_machine_test_asserts_negative.md`): **the test MUST fail if the flag-gate is removed** (path forced on). If deleting the gate leaves the test green, it asserts the happy path, not the invariant — that is a §3.5 watchpoint failure; surface it. A clean-posture story that is a trivial always-skip is invalid.

- **ADR-015 participant-floor + pseudonym pins — make them LOAD-BEARING, not named** (per `.claude/rules/advisor-orchestrator.md` §2.4a + `feedback_cheap_model_arm_drops_adr_constraints.md`):
  1. **Participant-floor on fetch:** name the gate — the recording-fetch handler MUST reject a non-participant request before serving the recording (or its URL). The authz source is the room participant set / `actor_pseudonym` mapping (ADR-015), checked at fetch time. Cite the fn + callsite the planner picks.
  2. **Pseudonym in the chain entry:** the `room_recording_uploaded` payload carries the actor/`chair_pseudonym` and any `speakers` as PSEUDONYMS — NEVER `person_id`/username/MXID. Under `always_pseudonym` a real identity in the entry (hash-chained, append-only) is permanent and unrecoverable — a leak breaks the `always_pseudonym` guarantee for the whole M3 cluster.
  3. **DoD lines:** (a) the fetch test asserts a non-participant request is rejected AND a participant request succeeds (Success Criteria line 144); (b) the chain-entry test asserts every identity-bearing payload field (`speakers`, actor) is a pseudonym string, never a numeric `person_id` or `@user:domain` MXID. DoD grep per §2.4a: `grep <participant-floor-fn> <fetch-handler>` returns BOTH the definition AND a callsite in the fetch path.

- **`always_pseudonym` Egress-leak guard** (PRD risk row 201). The identity→pseudonym mapping is at JWT-issue time (m3-core-infra), so the overlay is on the LiveKit-rendered stream and Egress captures the PSEUDONYM overlay. The §16a recording story should assert the LiveKit server never receives the real identity (mirror the infra-phase JWT identity test) OR cite that the infra-phase test already covers it and the recording path inherits it. Do NOT silently assume — name where the guarantee is tested.

- **Generic S3 API, no hardcoded MinIO hostname** (watchlist #5, D5 decision). The bridge speaks a generic S3 API so an operator can swap real S3/R2. The MinIO endpoint comes from config/env, NOT a hardcoded `minio:9000` in bridge source. Gate: `grep -rn "minio\." services/bridge/src/` returns nothing after impl (or only comments). A §13 task hardcoding the endpoint is a scope violation — catch-fire (bootstrap §7).

- **Content is never hashed beyond `content_sha256` (ADR-016 backplane contract).** Only recording METADATA (`{media_url, content_sha256, duration_s, speakers, attendance_count, actor_pseudonym}`) reaches the chain. The MP4 bytes themselves are stored in MinIO, NOT sent to `append_room_event`. `post_room_event` is metadata-only; the `content_sha256` is the ONE hash of the bytes, computed bridge-side, sent as metadata.

- **Bridge compiles + tests on Linux only.** Every `services/bridge/**` task's DoD = a `validate-pending-laptop-linux` DQ; the cargo command is `scripts/brehon/cargo-linux.sh check --manifest-path services/bridge/Cargo.toml` (and the integration test runs via `cargo-linux.sh test --manifest-path services/bridge/Cargo.toml`). The Windows-local `cd services/bridge && cargo` form is a DoD-issue (`ruma-common` E0119). The §15 commands MUST be written in the EXACT form the advisor runs at gate 1 (per `feedback_plan_dod_dry_run_at_write.md`) — dry-run them mentally before committing the plan. **The S3-dep task's `validate-pending-laptop-linux` gate is the headline risk** (new deps may not resolve clean on Linux even when listed; `Cargo.lock` resolution may surface a licence/version conflict — the bootstrap §2 flags LiveKit Egress Apache-2.0 + MinIO AGPL-3.0 as licence-clean but "verify at Cargo.lock resolution time").
