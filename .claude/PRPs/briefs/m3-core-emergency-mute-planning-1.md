## 2. Scope

Plan **all of M3-core-emergency-mute Phase 4 in one plan**. Source: `.claude/PRPs/prds/m3-town-halls-rtc.prd.md` §"Phase 4: M3-core emergency-mute" (lines 240–243) + §Technical Approach (174–203, esp. the federation-wide-mute risk row at 198) + §Success Criteria emergency-mute row (line 141) + OQ-V2-06 (lines 70, 242).

The plan's §13 tasks cover (planner finalizes count + `[P]` markers + ordering):

1. **Mute-all enactment across federated instances (the load-bearing mechanism).** A chair (or moderator with room-admin authority) drops EVERY non-chair publisher in the town-hall room — **including participants whose home instance is a different federated bridge** (OQ-V2-06: chair authority is room-global, Matrix power-level semantics). The enactment is via **Matrix `m.room.power_levels`** — MIRROR the existing machinery in `sanction_handler.rs` (`get_power_levels` `:281`, `put_power_levels` `:304`, `compute_power_override` `:266`), NOT LiveKit grants. See §4 "mechanism decision" — the planner MUST resolve, with a file:line cite, whether enactment is (a) a power-level PUT only (mirrors sanction_handler; cross-instance propagation is the <500ms risk), (b) power-level PUT + a LiveKit `RevokePublish` sweep of locally-known publishers for instant local effect (belt-and-suspenders), or (c) something the planner justifies. The PRD §Phase 4 says power-levels; the older `docs/.../V2/messaging.md:188` mentions re-granting LiveKit publish permissions — these are NOT the same code path; the planner reconciles them and picks one, citing both.

2. **`room_mute_all` chain emission (FIRST emission — emit-only, const ALREADY REGISTERED).** Wire the bridge to emit `room_mute_all` (`{chair_pseudonym, federated: true|false}` per Success Criteria line 141) on a mute-all action by pushing an `EmitIntent` to `Stage::pending_emits` — EXACTLY as `chair_override`/`transfer_chair` already do (`stage.rs:217,253,295`). The async controller drains it via the EXISTING `room_event_client::drain_emits` (`room_provisioner.rs:350`) → `post_room_event` → binary `/governance/room-event`. **The callback client EXISTS (stage-mode built it); the const EXISTS (`governance_log.rs:255`). Do NOT build a new emitter and do NOT re-declare or re-register the const.**

3. **<500ms publisher-client latency measurement (the marquee DoD).** The §16a marquee story asserts that all publishers are dropped within 500ms measured **at the publisher client** (not the server), **across two federated bridge instances**. Decide at plan time (see §4): the deterministic unit test of the mute-emission path (power-level PUT issued + `room_mute_all` EmitIntent queued with `federated: true`) is the GATE; a docker-gated `#[ignore]` cross-instance integration test (mirroring stage-mode's `stage_mode.rs` harness) carries the real <500ms cross-instance signal. The unit DoD gates the phase; the integration test is Phase-6-pilot-grade.

**Explicit boundaries — do NOT plan:**
- **No new entry-kind const, no registry-count bump.** `ENTRY_KIND_ROOM_MUTE_ALL` is at `crates/db_schema/src/source/governance/governance_log.rs:255`, registry count already 69→72 (m3-core-entry-kinds, Phase 2). A plan that re-declares the const or bumps the count is a SCOPE ERROR — stop and raise a `kind: "blocker"` DQ (bootstrap tripwire).
- **No LiveKit-grant-based chair/mic-passing logic** — that's stage-mode (Phase 3, shipped). Emergency-mute reaches for power-levels, not `GrantSink`/`GrantCmd`, for the cross-instance hammer (a local `RevokePublish` sweep is permissible ONLY as the option-(b) belt-and-suspenders, never as the cross-instance mechanism).
- **No MinIO / LiveKit Egress / recording / `room_recording_uploaded`** (Phase 5).
- **No new migration.** m3-core-infra shipped the `bridge_room` RTC columns; emergency-mute is mute-logic + chain-emission. If the plan introduces a `services/bridge` embedded-schema column or a `crates/db_schema/migrations/**` migration, surface it as a `kind: "blocker"` DQ before authoring §13 around it (bootstrap tripwire).

## 4. Constraints (enforce in the plan)

- **Mechanism decision is the FIRST scope decision (LOAD-BEARING).** The plan §13 MUST state, with a file:line cite, whether emergency-mute enacts via (a) Matrix power-level PUT only (mirror `sanction_handler.rs:304`; cross-instance propagation latency is the <500ms risk), (b) power-level PUT + a local LiveKit `RevokePublish` sweep for instant in-instance effect (the power-level PUT remains the cross-instance authority), or (c) a planner-justified alternative. The PRD §Phase 4 (line 242) says power-levels; `messaging.md:188` mentions LiveKit re-granting — the planner reconciles these explicitly. **The cross-instance authority MUST be power-levels** (OQ-V2-06); a plan that uses ONLY LiveKit grants for the cross-instance hammer is a mechanism error (catch-fire — bootstrap §7). Raise a `kind: "blocker"` DQ if the reconciliation is genuinely ambiguous; otherwise pre-seed the recommendation with both cites.

- **ADR-015 pseudonym pin — make it LOAD-BEARING, not named** (per `.claude/rules/advisor-orchestrator.md` §2.4a + `feedback_cheap_model_arm_drops_adr_constraints.md`):
  1. Name the gate: the `room_mute_all` chain entry carries `chair_pseudonym` (the actor who triggered the mute) — NEVER `person_id`/username/MXID. The pseudonym comes from the same allocator the JWT mint + stage-mode entries use (`actor_pseudonym` helper on the binary side, surfaced to the bridge via the `EmitIntent.actor_pseudonym` field).
  2. Why it can't be deferred: a real identity in a chain entry is permanent (hash-chained, append-only) — it cannot be scrubbed later, so a leak here is unrecoverable and breaks the `always_pseudonym` guarantee for the whole M3 cluster.
  3. DoD line: the test asserting the `room_mute_all` chain entry MUST assert the `chair_pseudonym` payload field is a pseudonym string, never a numeric `person_id` or an `@user:domain` MXID. The `federated` boolean is asserted too (`true` for cross-instance, per Success Criteria line 141).

- **Content is never hashed (ADR-016 backplane contract).** Only mute METADATA (`{chair_pseudonym, federated, room, at}`) reaches the chain. Speech/video bytes are NEVER hashed or sent to `append_room_event`. `post_room_event` is metadata-only.

- **<500ms is a TESTED, measurable DoD — not a vibe** (watchlist #6). The §16a marquee story asserts the publisher-client cross-instance measurement. The deterministic unit test (power-level PUT issued + EmitIntent queued) is the GATE that blocks the phase; the docker-gated `#[ignore]` cross-instance integration test (mirror `stage_mode.rs`) carries the real <500ms signal. A §16a story that asserts mute-all via a prose claim, with no measurable test, is a §3.5 watchpoint-specificity failure — surface it. **PRD fallback (line 198): if cross-instance <500ms proves infeasible, the plan documents a best-effort SLA + in-instance <500ms guarantee and surfaces a DQ before declaring the criterion failed — it does NOT silently drop the bar.**

- **Reuse the emit seam — do NOT rebuild it** (watchlist #2). The `room_mute_all` EmitIntent pushes to `Stage::pending_emits` and drains through the EXISTING `room_event_client::drain_emits`. Gate: `grep -rn "ENTRY_KIND_ROOM_MUTE_ALL\|room_mute_all" services/bridge/src/` must, after impl, return the EmitIntent push site (a `pending_emits.push` with `entry_kind`), NOT a new POST client. If the plan §13 includes "build the bridge→binary callback client," that's a scope error — stage-mode already built it (`room_provisioner.rs:350`).

- **Power-levels ≠ LiveKit grants** (watchlist #3). The cross-instance mute path is Matrix `m.room.power_levels` (mirror `sanction_handler.rs`). The plan must NOT conflate this with the stage-mode `GrantSink`/`GrantCmd` LiveKit machinery for the cross-instance hammer. Watch for a §13 task that reaches for `mint_access_token` to "revoke publish federation-wide" — that does not cross instance boundaries.

- **Bridge compiles + tests on Linux only.** Every `services/bridge/**` task's DoD = a `validate-pending-laptop-linux` DQ; the cargo command is `scripts/brehon/cargo-linux.sh check --manifest-path services/bridge/Cargo.toml` (and the integration test runs via `cargo-linux.sh test --manifest-path services/bridge/Cargo.toml`). The Windows-local `cd services/bridge && cargo` form is a DoD-issue (`ruma-common` E0119). The §15 commands MUST be written in the EXACT form the advisor runs at gate 1 (per `feedback_plan_dod_dry_run_at_write.md`) — dry-run them mentally before committing the plan.

- **Cargo.lock sync on any dep add.** If a task adds a `services/bridge/Cargo.toml` dependency, the regenerated `Cargo.lock` MUST land in the SAME commit. Emergency-mute likely needs NO new dep (reuses `reqwest` for the power-level PUT, the existing `room_event_client`, `rusqlite`); flag if it does.

- **Watchpoint specificity** (§3.5 gate, per `feedback_advisor_watchpoint_specificity.md`): every §4 watchpoint cites a specific file:line / fn — e.g. "watch the mute path issues `PUT /state/m.room.power_levels` per `sanction_handler.rs:304` against EVERY federated room, not just the local one", not "watch cross-instance mute".

Each cites its integration-test fn name and asserts on observable Matrix/chain state, not config.
