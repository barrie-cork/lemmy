## 0.2 The ONE genuine design fill-in PRD §9 leaves open (the clarify-gate's primary target)

PRD §9.4's `receive_remote_moderation_label` body has a literal fill-in placeholder:

```rust
peer_trust_level_at_receipt: /* from wrap_governance_inbound context */,
```

`wrap_governance_inbound` computes the peer trust level at step 1 (`let trust = federation_inbox_check_peer_trust(...)`). The label handler (and any other handler that persists `peer_trust_level_at_receipt`) needs that resolved value threaded through the wrapper's `inner` closure. PRD §9.2's signature is:

```rust
pub(crate) async fn wrap_governance_inbound<F, Fut, A>(activity: A, context: &Data<LemmyContext>, inner: F) -> LemmyResult<()>
where F: FnOnce(A, &Data<LemmyContext>) -> Fut, ...
```

— the `inner` closure receives only `(activity, context)`, NOT the resolved `trust`. **This is the one genuine design decision PRD §9 leaves open and the planner must resolve it in the plan (it is NOT pre-resolved here — it is the primary clarify-gate target).** Candidate shapes the planner evaluates (the planner picks one and states it in §10 with a rationale; or files a `kind: "blocker"` if none is defensible):

1. Widen the `inner` closure signature to `FnOnce(A, &Data<LemmyContext>, FederationPeerTrust) -> Fut` so the wrapper passes the resolved `trust` into the handler. (Changes PRD §9.2's signature — but PRD §9.2 says "extend the mapping if needed" elsewhere; a closure-arg widen is in-spirit. The 3 per-handler patches' closures gain an unused `_trust` param; only the label handler reads it.)
2. The label handler re-queries `federation_inbox_check_peer_trust(peer_domain, conn)` itself inside `inner` (a second DB read; the wrapper already did one — minor redundancy, but zero signature change and the simplest mirror of the existing helper).
3. Thread the trust via a typed extension on `context` / a request-scoped value (heaviest; likely over-engineered for v1 — flag if proposed).

The advisor's lean (NOT binding — the planner decides): option 2 is the lowest-risk v1 shape (no signature change, no closure-arg churn across the 3 patched handlers, mirrors the existing `federation_inbox_check_peer_trust` helper exactly; the redundant second read is negligible — it is a single indexed lookup, and v1 is advisory-only / not hot-path). Option 1 is cleaner long-term but changes the PRD §9.2 signature and ripples into all 3 per-handler patch closures. The planner weighs this and **records the decision + rationale in the plan's §10 + a `kind: "log"` entry**; the advisor surfaces it at the clarify-gate either way (`/brehon-clarify` will raise it as a `kind: "clarify"` DQ — this is expected and is the gate's main job for this sub-phase).
