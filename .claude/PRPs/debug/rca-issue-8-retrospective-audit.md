## Re-validation of the one surviving "success" signal

`.claude/audit-5b-regression.log` is the only cargo-test.bat "success" log in the window whose exit code was load-bearing for a phase-5b regression conclusion. Because the log shows the test binary actually executed (`running 1 test` + `test result: ok; 1 passed; 0 failed ... finished in 57.14s`), the success is necessarily genuine — the exit-code mask only kicks in when cargo itself returned non-zero, but this log shows cargo completed and handed off to the test runtime which then reported a passing result. A false-greened invocation (like `tmp/repro.log`) stops at `error:` and never produces "running 1 test" output.

Just to be completely sure, we re-ran the same command under the fixed wrapper:

```bash
cmd //c "scripts\\brehon\\cargo-test.bat --test e2e -p lemmy_server sponsor_liability_with_founder_multiplier --no-run > .claude/verify-5b-recompile.log 2>&1"
# exit code: 0
# Finished `test` profile [unoptimized] target(s) in 2m 11s
```

Exit 0 under the fixed wrapper. The 5b regression result stands.

## What signals are NOT suspect, and why

Logs dated before `e7cad24fd` (2026-04-18 19:28:03) used the pre-guard `cargo-test.bat`, which had a single terminal `cargo.exe test %*` line with no intervening `goto :eof`. The exit code propagated naturally. The bug was introduced *by* Move 7, not by the wrapper's pre-existing shape — so **everything logged before Move 7 is safe**.

Logs generated by `cargo-check.bat` in the window are also safe, because cargo-check.bat did not have the `goto :eof` clobber pattern until the preventative fix added `exit /b !errorlevel!` to it today. Its single terminal line propagated by accident. (The preventative fix makes that propagation explicit so future edits can't reintroduce the bug class.)

## Why only one invocation was at risk

The false-green bug only surfaces when **cargo itself** returns non-zero before a test can run (pre-compile errors like `does not contain this feature`, `no test target named X`, or compilation failures). In the 30-minute window:

1. Most cargo-test.bat invocations ran against known-good configurations and genuinely passed.
2. Cargo-check.bat invocations were immune (different wrapper).
3. The user was specifically re-probing the 5b regression, which is a single deterministic test that either compiles and passes or fails with a diagnostic. The first probe (`tmp/repro.log`) hit a pre-compile error (`--features full` against a crate that doesn't expose `full`), which was the false-green. The user noticed the mismatch ("wrapper says 0 but log says error"), filed issue #8, and re-ran without the bad flag to get the actual signal.

Put simply: the user found this bug by noticing the discrepancy in the exact invocation that triggered it, then immediately worked around it by removing the bad flag. There was no opportunity for an undetected false-green to poison a downstream decision — the surrounding investigation *was* the decision.

## Preventative posture going forward

Two changes shipped on `phase-5c` before this audit:

1. **`bb254e733`** — exit-code propagation fix in both wrappers.
2. **`61edf2665`** — new Probe 4 in `.claude/rules/pre-phase-harness-audit.md` §1 that asserts non-zero exit on bogus `--features`. Any future wrapper edit that reintroduces the bug class will be caught at pre-phase audit, not at a downstream false-green.

No additional retro work is required.

## What would have been required if the audit had found a suspect signal

For completeness, if a load-bearing "success" had been identified as potentially false-greened, the remediation path would have been:

1. Identify the exact command that produced the log.
2. Re-run under the fixed wrapper.
3. If the new result is red, the prior decision (DoD pass, checkpoint green, PR merge-readiness) needs to be revisited — this might mean reopening a merged PR, re-examining a phase-close report, or retrying a skipped task.
4. Log the discrepancy in the phase retro and a feedback memory.

None of steps 1-4 apply here. The single false-greened invocation was immediately retried by the user and fixed.
